7. More thorough e2e testing with policies to verify features. The idea here is that if we want to verify a feature or the system works as intended: e.g if alert notifications fire as intended, or if we want to verify that the trajectory of the plan recommendations are correct, we should define policies to test with.

-   E.g begin test with a "reluctant policy". for whatever plan is returned that day, only fulfill by a certain percent. Have pain score be constant / not improving. Expected behaviour is for app notifications for user wellness to be raised due to low compliance with plan + not improving pain score. Policy here is what a subagent will condition itself to respond with, yes a subagent will be creating a harness for yourself to interact with the plan. This is to prevent context contamination to you, the main agent, who is in charge of the loop.

The idea for this part is to fully simulate app-patient interactions. Create a harness for you to respond to plans i.e a feedback loop between you and the system. Your conditioning should be the onboarding outputs, the policy, and some longer running memory in markdown files you increase somewhere for each test session, just in case you run out of context.

The harness you create should accept a policy argument, e.g npm run harness:name_of_test policy="LENGTHY_POLICY_STRING_HERE". The idea is that for a particular app interaction we want to test, we can pass in a detailed policy to condition the subagent on-the-fly.

Ensure detailed but succinct logging. For each app-patient interaction the subagent has, log the response to the plan task-wise e.g log leglifts 7/10 where 7 is the chosen amount done for the exercise.
